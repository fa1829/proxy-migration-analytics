# proxy-migration-analytics

Readiness analytics for moving applications from a legacy on-prem web proxy to a cloud Secure Web Gateway (Netskope), built around the questions a migration team actually has to answer before each wave:

1. **Who uses each app, how much, and what does the proxy currently do to it?** (baseline)
2. **Which apps cannot be TLS-inspected** — certificate pinning, mutual TLS, non-443 ports — and does each one have a current, approved exception?
3. **Which denies are intended controls and which are policy gaps** that would be copied into the new platform if migrated blindly?
4. **Which exceptions are expired, unused, or missing a change ticket** (audit-trail gaps to escalate, not migrate)?
5. **What traffic has no owner at all** (shadow IT) and must be decided on before cut-over?
6. **Is the log feed itself trustworthy?** (node volume drops, missing user fields)

It ships the same logic twice: as a **Splunk SPL library + dashboard** (`splunk/`) and as a **pandas implementation** (`analyzer/`) that runs and is unit-tested without a Splunk licence.

> All data is synthetic, generated by `generator/generate_logs.py`. Application names are used only to make the data recognisable; nothing here reflects any real organisation's traffic or configuration.

## Quick start

```bash
pip install pandas pytest
python generator/generate_logs.py          # 14 days x 3,000 events -> sample_data/
python analyzer/analyze.py                 # -> output/report.html, app_readiness.csv, ...
pytest -q                                  # 10 tests
```

Run the SPL against real Splunk (lab use):

```bash
export SPLUNK_PASSWORD='choose-a-strong-one'
docker compose up -d                       # http://localhost:8000, user admin
# app "Proxy Migration Analytics" -> dashboard "Proxy to Netskope migration readiness"
```

## What the sample run finds

| App | Verdict | Why |
|---|---|---|
| Office 365, Salesforce, ServiceNow, Workday, Refinitiv | READY | Clean decrypt + allow; mirror policy, pilot one BU |
| Bloomberg Terminal, SWIFT Alliance | READY WITH POLICY | Can't be inspected (pinning / mTLS) but exception is current → Do-Not-Decrypt rule |
| Zoom | NEEDS WORK | Pinned **and** its exception expired 2026-09-30, plus a sub-domain bypassing with no exception |
| GitHub, Docker Hub | NEEDS WORK | ~35% of requests hit `deny-dev-tools` — intended control or gap? Owner must decide |
| Vendor FX Feed | NEEDS WORK | Port 8443 (needs a service profile) and an expired exception with no change ticket |
| Dropbox, Pastebin | BLOCKED: no owner | Not in inventory; one user uploads ~2.7 MB vs a median of a few KB |

## Layout

```
generator/generate_logs.py     synthetic proxy + SSL-bypass logs, lookups (inventory, exceptions, users)
analyzer/analyze.py            readiness verdicts, control gaps, anomalies, draft policy plan, HTML report
splunk/                        a Splunk app: spl/ (12 searches), props/transforms, dashboard, 2 scheduled alerts
tests/                         behaviour tests
docs/migration-runbook.md      the process this tooling supports
```

## Design decisions and honest limitations

- **Handshake failures are not counted as denies.** A pinned app that breaks under inspection looks like a 55% block rate. Treating that as a policy problem leads to the wrong fix (rewriting allow rules instead of adding a Do-Not-Decrypt rule). The two are reported separately.
- **Robust z-score (median/MAD) for upload anomalies**, plus a 500 KB floor. Mean/stdev lets a single large exfil inflate the stdev and hide itself; without the floor, apps with few users produce many statistically-odd-but-trivial hits. Both thresholds are starting points to tune on a pilot group, not truths.
- **The policy plan is a review artefact, not a Netskope import.** Real policies are built in the tenant (UI, REST API, or Terraform) after app-owner and security sign-off. Generating "ready to push" config from log statistics would skip the change-management step this role is required to follow.
- **Netskope field names** (`x-ssl-bypass`, `x-ssl-bypass-reason`, `cs-host`…) follow Netskope's documented transaction-event formats, but a tenant chooses which fields to stream and in what order. Validate against your Log Streaming configuration before trusting `12_netskope_ssl_bypass.spl`.
- **Unmapped domains are grouped by the last two labels** (`content.dropboxapi.com` → `dropboxapi.com`). That is wrong for multi-part public suffixes (`example.co.uk`); a real deployment should use the Public Suffix List.
- **The synthetic CSVs are CIM-shaped by construction.** Real proxy logs (Blue Coat/Symantec ProxySG, Zscaler, Palo Alto URL logs) need field extraction and normalisation first — usually the bulk of the effort. `11_palo_alto_url_equivalent.spl` shows the Palo Alto variant via the Splunk Add-on's `pan_url` eventtype.
- The SPL is written to Splunk syntax and the dashboard XML is validated for well-formedness, but the searches were developed against the pandas twin; run them on your instance before relying on them.
